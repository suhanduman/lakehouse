----------------------------------------------------------------------------
 INSTALL ORDERING (informational — enforced by Helm's native kind ordering +
 operator reconciliation + pod readiness, NOT by helm hooks; see
 operators/README.md "Kurulum sıralaması" section)
----------------------------------------------------------------------------
 Helm applies everything in one pass, then components converge in this order
 as operators reconcile and readiness probes retry:
   1. namespace / quota / limits / NetworkPolicy / StorageClass  (foundation)
   2. CNPG Postgres clusters + Kafka backbone + Apicurio          (stateful)
   3. Nessie + Trino + Kafka Connect + Spark + Keycloak app       (depends on 2)
   4. example connectors + Console + Kafka UI + Routes            (outermost)
 Hard data-dependencies (Nessie needs pg-nessie ready; Connect needs Kafka +
 Apicurio ready) settle automatically via operator reconcile + container
 restarts — transient CrashLoopBackOff during the first minutes is EXPECTED,
 not a failure. Watch convergence with:
   watch {{ $cli }} -n {{ include "lakehouse.namespace" . }} get pods,cluster,kafka,kafkaconnect

{{- if and .Values.components.trino .Values.components.keycloak }}

 *** IMPORTANT — Trino/Keycloak ordering is NOT interchangeable with the rest
 *** of "step 3" above, even though they're listed together:
   - Nessie's OIDC check is LAZY (Quarkus): the pod stays Running even if the
     Keycloak issuer isn't reachable yet; it only 500s on actual API calls
     until the issuer resolves. Nessie degrades SOFT.
   - Trino's coordinator does EAGER OIDC discovery AT STARTUP (fetches the
     issuer's OIDC discovery document before it will serve traffic). If
     Keycloak's realm/OIDC issuer endpoint is not YET reachable when the
     Trino coordinator starts, it throws and CRASH-LOOPS — it does not retry
     gracefully like Nessie. Trino fails HARD.
   Practical consequence: with `components.keycloak=true`, let Keycloak (the
   `Keycloak`/`KeycloakRealmImport` CRs + its {{ $routeWord }}) fully converge and its
   OIDC issuer URL become resolvable BEFORE relying on Trino coming up —
   don't assume "step 3" components converge safely in parallel. Verified
   live on microk8s with a deliberately non-resolving issuer: Nessie stayed
   Running (soft 500s), Trino's coordinator crash-looped on
   `UnknownHostException` (hard fail). See
   .superpowers/sdd/microk8s-smoke-report.md Finding 2 for the full repro.
{{- end }}

----------------------------------------------------------------------------
 nginx access-log ingest (FluentBit VM agent — runs OUTSIDE the cluster, on
 each nginx host, not as a pod; this chart only ships the two config files as
 a ConfigMap so they can be installed from one place)
----------------------------------------------------------------------------
  1. On each nginx VM: install FluentBit
       curl https://raw.githubusercontent.com/fluent/fluent-bit/master/install.sh | sh
  2. Pull the two files out of the ConfigMap this chart created and copy them
     to the VM:
       {{ $cli }} -n {{ include "lakehouse.namespace" . }} get configmap fluentbit-vm-agent -o jsonpath='{.data.fluent-bit\.conf}'  > fluent-bit.conf
       {{ $cli }} -n {{ include "lakehouse.namespace" . }} get configmap fluentbit-vm-agent -o jsonpath='{.data.fluent-bit\.service}' > fluent-bit.service
     Copy fluent-bit.conf -> /etc/fluent-bit/ on the VM (its Brokers/password
     lines come from `.Values.nginx.fluentbit.kafkaExternalBootstrap` /
     `.Values.nginx.fluentbit.kafkaPassword` — fill in real values
     per-environment before copying, current render: broker=
     {{ .Values.nginx.fluentbit.kafkaExternalBootstrap }}); also place the
     Kafka cluster CA at /etc/fluent-bit/kafka-ca.crt.
  3. Copy fluent-bit.service -> /etc/systemd/system/ on the VM, then:
       systemctl enable --now fluent-bit
  4. In the cluster (once, via Trino): create the Iceberg namespace the
     streaming job writes into (bucket mirrors
     `.Values.nginx.streaming.checkpointBucket`, default
